# 我的第一个公开作品：把 AI 品牌可见度观察做成一个工作台

我做 GEO Agent 时，最想解决的是一个衔接问题：当我们发现某条 AI 回答没有出现目标品牌，接下来该怎么办？

单独记录一张截图或一个百分比，往往还不足以支持行动。回答可能只是换了一种说法，也可能引用了不准确的品牌事实。补充内容后，如果下一次换了题目或模型，指标变化又很难解释。

所以，我把项目组织成一条工作流：品牌事实库、提问题集、回答样本、分析复核、优化任务、同题复测和报告交付。

## 先把观察对象说清楚

品牌在回答里出现，与品牌被推荐，是两件不同的事。一个回答可以提到某个品牌，却并没有把它列为适合用户的候选；也可能推荐了它，同时编造了资质、客户或能力。

GEO Agent 把这些判断拆开记录，并保留回到问题和回答的入口。规则与模型给出的判断需要人工复核，尤其是涉及品牌事实和外部证据时。

这里也有一个边界：API 联网近似采样不等同于产品客户端的排名。不同入口、模型、上下文和检索配置都会影响回答，不能把观察结果包装成统一的平台排名。

## 让建议有明确的下一步

一句「加强品牌内容」很难执行。我更希望建议能说明为什么要做、对应哪些问题、需要什么材料、交付什么内容、怎样人工验收，以及复测哪些题目。

因此，任务中心把建议、草稿、质量检查、人工批准、执行、交付和效果确认连接起来。完成交付并不自动意味着效果改善；系统需要保存比较预览，最后仍由人确认结论。

## 比较之前，先固定题目和条件

持续监测最容易误读的地方，是把不同条件下的结果直接比较。换题、换平台配置或者样本不完整，都可能让百分比发生变化。

项目保留固定题集和配置记录，并对周期比较设置条件。公开版使用虚构数据，因此不会把这些模拟批次当作真实监测趋势。

## 报告也是一个需要保存状态的产品

报告制作采用草稿、审核、保存版本和冻结 PDF 的流程。客户门户只读已发布内容，下载的 PDF 校验对应版本的摘要。这样，交付出去的内容可以追溯，而不是随着工作台数据变化悄悄改写。

工程上，前端使用 React、TypeScript 和 Vite；后端使用 Python 与 SQLite。现阶段后端仍比较集中，拆分身份、采样、证据和报告模块是后续可以继续改进的方向。

## 从内部项目到公开作品

公开版本需要重新设计体验的边界。我选择保留主体流程，用新的虚构品牌、题目和回答构建演示数据，没有沿用正式客户库、原品牌 Logo、凭据或内部部署材料。

公开版不需要 API Key。所有外部 HTTP 请求被强制阻断，后台自动采样和自动分析循环不启动。访客点击「生成一轮模拟样本」，就能在本机看到回答与分析记录的流转，不会产生 API 费用。

测试也重新界定范围：数据库测试使用临时文件，HTTP 测试从虚构种子生成独立工作区，覆盖网络阻断、数据关联、文件访问限制、PDF 冻结和门户行为。它验证的是这个公开演示版本，不能替代原产品或真实平台的完整验证。

这是我的第一个公开作品。我希望它能让人看到我如何把一个模糊问题拆成可操作的流程，也能看到这个流程还需要继续改进的地方。
